## 2. Comprehensive Audit Matrix (15 Core Findings)

### 1. Where documents are actually stored
- Physical uploaded files (PDF, DOCX, TXT, MD, CSV) are saved in `data/knowledge_base/` under a sanitized unique filename `{uuid.hex}_{clean_name}`.

### 2. Where document metadata is stored
- Authoritative document metadata is registered in SQLite `documents` table (`id`, `filename`, `source_path`, `content_hash`, `file_size`, `mime_type`, `chunk_count`, `owner_id`, `owner_username`, `status`, `created_at`, `updated_at`).

### 3. Where embeddings are stored
- Embedded chunk vectors (384-dimensional dense vectors generated by local `all-MiniLM-L6-v2`) are stored in ChromaDB `./vectorstore` with cosine similarity space.

### 4. Where conversations are stored
- Conversation session metadata is persisted in SQLite table `conversations` (`id`, `user_id`, `username`, `title`, `feature`, `status`, `created_at`, `updated_at`, `last_message_at`).

### 5. Where messages are stored
- Individual chat exchanges are persisted in SQLite table `messages` (`id`, `conversation_id`, `user_id`, `username`, `role`, `content`, `timestamp`, `rag_used`, `sources_json`, `model_id`, `duration_ms`, `request_id`, `verification`, `error_detail`, `feature`, `metadata_json`).

### 6. Where audit events are stored
- Audit records are stored in SQLite table `audit_logs` with HMAC-SHA256 hash chaining (`previous_hash`, `entry_hash`), user context attribution, action classification, request correlation ID, component, resource, and execution duration.

### 7. Where dashboard statistics come from
- **Document Count**: Real count of indexed documents retrieved via `GET /documents` and `GET /documents/stats`.
- **Conversation Count**: Real count of user conversations retrieved via `GET /conversations`.
- **Active Model**: Real active model discovered via `GET /models/active` (Ollama daemon).
- **Audit Summary**: Exact SQL aggregate queries from `GET /audit/summary`.

### 8. Which values were hardcoded
- Prior audit identified hardcoded metrics in dead UI tabs (which were removed). All production UI views now bind directly to dynamic React state populated by backend APIs.

### 9. Which values are mocked
- In unit testing files (`tests/`), isolated mocks test error boundaries.
- In production runtime paths (`backend/app/`, `backend/rag/`, `backend/security/`, `backend/agents/`), **zero mock data exists**.

### 10. Which values are generated at runtime
- Request Correlation IDs (`X-Request-ID` UUIDv4).
- Audit entry hashes (HMAC-SHA256 chained to previous row).
- Document chunk IDs (`{doc_id}_c{chunk_index}`).
- Session IDs (`conv_{uuid.hex[:12]}`).
- Timestamps (`datetime.now(timezone.utc).isoformat()`).

### 11. Which API endpoints provide each value
- `GET /documents`: Authenticated document array.
- `GET /documents/stats`: Document count and chunk totals.
- `GET /conversations`: User's scoped conversation sessions.
- `GET /conversations/{id}`: Conversation thread messages.
- `GET /audit/summary`: Real audit totals by action category.
- `GET /audit/logs`: Filtered audit events array.
- `GET /models`: Discovered local Ollama model profiles.
- `GET /models/active`: Current active LLM.
- `GET /auth/me`: Authenticated user profile and permissions.

### 12. Whether multiple databases/stores are being used inconsistently
- Single SQLite database `data/private/aegis_auth.db` stores all relational entities (`users`, `audit_logs`, `conversations`, `messages`, `documents`, `revoked_tokens`).
- ChromaDB `./vectorstore` is strictly used for vector indexing and semantic retrieval.

### 13. Whether the frontend has fallback/mock data
- Frontend components use explicit truthful empty states:
  - 0 documents: `"0 documents"`, `"No indexed documents found."`
  - 0 conversations: `"0 conversations"`, `"Start a secure local conversation to begin."`
  - 0 audit logs: `"No recorded activity yet."`

### 14. Whether backend services have fallback/mock data
- Backend endpoints return explicit HTTP 404 / 400 errors or empty arrays (`[]`, `{"count": 0}`) when resources do not exist.

### 15. Whether seeded/sample records are being loaded automatically
- `scripts/seed-users.py` exists solely as an explicit CLI script for initial developer accounts and is not called automatically on server startup.
- Tables start empty on a clean database.
